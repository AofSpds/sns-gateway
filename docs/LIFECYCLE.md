## 소스 연결

설정에서 소스1개를 선택한다. Galaxy는 Storage Access Framework의 외부저장소 로컬 폴더를 읽기 권한으로 연결하고, iPhone은 사용자가 만든 PhotoKit 앨범을 선택한다. 최초 목록은 baseline이며 기존 항목을 게시함에 쏟아 넣지 않는다. 소스를 바꾸거나 재연결하면 새 baseline을 만든다.

완전한 목록을 얻은 뒤 DB snapshot을 갱신한다. 2,000개 초과·권한 철회·조회 실패는 부분 목록 성공으로 기록하지 않는다. Android 하위 폴더·클라우드 공급자는 제외한다. iOS 제한된 사진 권한은 전체 앨범 목록이라고 가정하지 않으며 직접 가져오기 안내로 돌아간다. 앨범 선택 목록 상한은100개다.

앱 재개/새로고침에서 회차당 신규10장을 가져온다. 반복/삭제후 재등장한 동일 소스 identity는 기존 항목으로 남고, 편집된 항목은 revision key로 구분한다. 가져오기 실패는 PENDING에 남아 다음 시도 대상이다. iCloud-only 원본은 네트워크를 켜서 가져오지 않는다.

외부 소스의 파일 수정일·자산 수정일은 membership 추가시각이 아니다. 성공적으로 가져와도 FIRST_OBSERVED와 등록시각null을 보존하고 사용자 날짜 확인 뒤 수동 포함한다. 이미 앱에 같은 사본이 있다면 기존 등록시각을 보존한다. 정확한 등록일 자동 선정을 원하면 앱에서 사진을 직접 가져온다.

## 날짜 묶음

한국 시간 service_date와 revision으로 사진순서·문구를 보관한다. 수정은 기존 revision을 UPDATE하지 않고 새 revision을 INSERT한다. expected revision 충돌은 덮어쓰지 않는다. 공유 시점의 사본·문구와 해당 revision을 연결하므로 나중에 다른 문구를 써도 이전 이력이 바뀌지 않는다.

날짜를 닫으면 수정할 수 없다. 다시 열기를 선택하면 편집할 수 있으나 이미 정리된 사본을 복원한다고 보장하지 않는다. '사용 가능한 사본만 남기고 저장'으로 명시적 새 버전을 만들 수 있다. 날짜 이동 전 수정한 문구는 저장한다. 본래 v2의 전역 문구는 새 날짜의 초기 문구로 보존한다.

## 오래된 알림

Android 새 알람에는 원 due 시각을 넣고 해당 KST 날짜를 알림 launch intent와 기기 설정에 저장한다. 업그레이드 전 알람처럼 due가 없으면 DELIVERY_DATE로 남긴다. iOS 반복 캘린더 알림에서는 UNNotification.date(전달일)를 보존한다. 앱을 연 날짜로 대체하거나 전달일을 원 예정일이라고 주장하지 않는다.

알림 탭을 앱 시작 전 native 경계에서 기록하고 날짜 확인 패널을 표시한다. 사용자는 표시 날짜 또는 오늘을 명시적으로 고른다. 다른 날짜는 날짜 입력으로 연다. 확인 후에만 pending context를 지운다. 사진 마감은09:00이며 늦게 열었다고 창을 늘리거나 자동 전송하지 않는다. 알림 OFF/초기화 시 앱의 pending/delivered 알림도 정리한다.

## 보존·삭제

500MiB 제한은 앱의 관리 대상 JPEG 사본과 공유 staging 합계다. DB/로그/OS 캐시 전체 사용량을 포함한 기기 저장공간 상한이 아니다. 원본은 수정·삭제·이동하지 않는다. 파일 한 장10MiB, 최대 변2048px 경계는 유지한다.

자동 정리는 다음 모두를 만족해야 한다: 모든 참조 날짜가 명시적으로 완료/폐기로 닫힌 지7일 이상, 해당 사진의 모든 공유가 사용자 완료/취소 또는 관측된 취소로 해결된 지7일 이상. 아무 묶음에도 쓰이지 않은 미공유 inbox와 미확인 공유는 보호한다. 오래된 미참조 staging은7일 유예 후 정리한다. 파일 사본은 삭제되어도 사진 식별자/이력/당시 문구는 남긴다.

선택 사본 수동 삭제는 확인 창을 거치며 미확인 공유는 보호한다. 최근 staging은 이 동작으로 삭제하지 않는다. 요청한 파일 전체를 native의 canonical 경로·이름 whitelist로 검증한 뒤 실행한다. 원본·DB·허용 루트 밖·symlink 외부 대상은 거부한다.

삭제 전에 file_deletions journal과 PURGING 상태를 저장한다. 실제 삭제 성공/이미 없음이 확인된 경우에만 PURGED를 기록한다. 중단/실패는 다음 앱 재개에서 재시도한다. 동일해시 사본이 다시 들어와도 tombstone을 적용해 삭제한 사진이 자동으로 부활하지 않게 한다.

전체 초기화는 명시적 확인과 reset_pending journal을 사용한다. 미확인 공유는 먼저 사용자 결과 확인이 필요하다. 알림OFF→소스해제→앱 관리 파일삭제→DB 행정리 순서이며 schema version은 유지한다. 중간 실패 시 다른 작업보다 reset을 먼저 재개한다. 개인 기기의 전체 데이터나 SNS 원격 게시물 삭제가 아니다.

## 검증과 남은 수락

Node/SQLite 하네스는 실제 TS 저장·서비스 코드를 실행하고 파일/OS 경계만 fixture로 바꾼다. 네이티브 파일삭제 whitelist는 실제 Swift Foundation 코드로 합성 파일 시험을 한다. 두 시험 모두 iPhone/Galaxy 실기 수락을 대신하지 않는다.

실제 기기에서 필요한 수락: 선택권한/철회, 신규파일/앨범편집, iCloud-only 제외, 대량소스 한계, 메타데이터, 닫기7일 경계, 저장공간 부족, cold/warm 알림tap, 자정/시간대 변경, reset중단, SNS 단일/다중/문구/취소. 실기·독립 IVA·병합·배포는 미실행이다. API 키와 외부 서버는 추가하지 않았다.
